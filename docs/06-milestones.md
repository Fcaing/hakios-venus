# 项目时间线与两条技术路线

---

## 1. 两条路线，先分清

这个工程目录里其实有**两条互不相干的路线**，读文档时很容易混：

| 路线 | 目标 | 现状 | 结论 |
|---|---|---|---|
| **A. HakiOS**（XNU `8796.121.2` / Darwin 22.5 / **iOS 16.5 20F66**） | 在 venus 上把 iOS 跑起来并驱动硬件 | **已能开机、能触摸、能显示、能装内置应用**；Wi-Fi 卡在固件侧 | ✅ 这是主线，所有可用功能都在这一条上 |
| **B. UniXNU**（iOS 26.5.2 `23F84` / arm64e） | 用 UniXNU 的构建体系做 iOS 26 | 内核能编出来（23.4 MB），payload 能引导到内核入口；**卡在 `_arm_vm_init` 极早期**；评估认为到 SpringBoard **不可行** | ⏸ 已停。硬阻塞是 GPU（Adreno 660 没有也不会在 Metal 后端）与 SEP（keybag/生物识别/DRM） |

**选哪条**：如果目标是"这台手机日常能用"，**只能走 A**。B 的天花板（社区最好水平 = Surface Duo 2 的 zeta：内核 + APFS + 改写后的 launchd 首进程）在 venus 上连主屏幕都到不了。
B 的价值只剩"内核构建/引导链"的经验，**不要再往 B 投时间**。

## 3. 每一轮实验的"标签"怎么读

日志里的 `apply-NNN` 与 `pNNN` 是两个编号体系：

| 编号 | 含义 |
|---|---|
| `apply-NNN` | **补丁编号**，对应 `history/patches/applyNNN.py`；一个补丁 = 一次代码改动 |
| `pNNN` | **轮次编号**，对应 `pNNN.txt` / `cur-pNNN.bin` / `p-pNNN.bin`；一轮 = 一次冷启动上机 |

两者不是一一对应：同一轮可能带多个补丁，同一个补丁也常在多轮里重复出现。
`history/INDEX.md` 是 `apply-NNN` 的索引。

## 5. 复盘：哪些判断错了，错在哪

| 错的判断 | 错的类型 | 教训 |
|---|---|---|
| "M4 卡在 PBL 不跳转" | 现象命名错 | 其实是 MSI 使能位；**命名现象时不要绑定因果** |
| "设备从未碰过通道上下文" | 观测偏差 | 那一轮主机自己已经写过上下文，于是把"自己写的值"当成"设备没动" |
| "命令环只在 boot 窗口可用" | 以偏概全 | 是 `nom0/late0` 的时序 + 单条 TRE 的 wp 语义，不是引擎限制 |
| "`amss.bin` 是 ARM Thumb-2" | 前提未验证 | 先用统计判据（`bx lr` 出现频率）验证指令集，再开始反汇编 |
| "RDDM 拿到 dump 了" | 假阳性 | 缓冲区落在镜像区，读到的是自己拷进去的固件 |

**共同的教训**：每个结论都要有一个**正对照**（LOOPBACK 通道就是最好的那个），否则"设备没反应"和"我们没发对"永远分不开。
