## 0. 一分钟版

**目标**：在小米 11（代号 **venus**，M2011K2C，SM8350 + 外挂 QCA6490/WCN6855 Wi-Fi 芯片）上，让移植的 XNU（HackiOS）用自己的 PCIe + MHI 驱动把 Wi-Fi 用起来。

**当前位置**：PCIe 链路、BHI/BHIE 固件下载、MHI 控制面全部打通；MHI **数据面**也已经在 LOOPBACK 通道上双向跑通（主机写进去的字节原样从环回通道回到主机缓冲区）。
**唯一卡点**：QCA6490 的 AMSS 固件启动后（EE=2、MHISTATUS=0x201）**不服务 IPCR 通道（ch20/ch21）**——命令环不取、数据环不取、M2 请求不认。Wi-Fi 的 QMI 只走 IPCR，所以 Wi-Fi 到这里就断了。

**下一件事**：对 `amss.bin` 做真正的反编译（Thumb-2），从 `ipc_router_xal_up` 往上追调用者，找出固件侧"传输对象 xport 什么时候被创建"。或者按 §7 的方案 C 转做上层。

### 1.1 芯片命名与固件选择（2026-11-11 核实）

结论：**是外挂 QCA6490，也就是上游所说的 WCN6855；不是 QCA6391，也不在 SM8350 内部。**

- 真机 DTS（`phone-dump\venus-hw\venus-live.dts`，工作区根下）：`:12857` `qcom,cnss-qca6490@b0000000 { compatible = "qcom,cnss-qca6490"; ... }`，`:13100` `bt_qca6490 { compatible = "qcom,qca6490"; }`，`:22612` 它挂在 `pcie@1c00000/pcie0_rp/cnss_pci` 下。**独立 PCIe 端点、自己的 AMSS/EE/BHI** ⇒ “外挂”成立；SM8350 自身没有 WLAN MAC/PHY。
- 厂商驱动：`drivers/net/wireless/cnss2/bus.h:19` `#define QCA6490_DEVICE_ID 0x1103`；`main.c:2753` `{ .name = "qca6490", .driver_data = QCA6490_DEVICE_ID }`。本机 PCI ID 正是 `17cb:1103`。该驱动里**没有 QCA6391**（只有 QCA6390=`0x1101`、QCA6490=`0x1103`）。
- 上游命名：ath11k `pci.c:32` `#define WCN6855_DEVICE_ID 0x1103` —— 同一个 ID 叫 WCN6855；`core.h:145` 的 `enum ath11k_hw_rev` 里也没有 QCA6490，只有 `ATH11K_HW_WCN6855_HW20/21`。所以 **QCA6490 与 WCN6855 是同一颗芯片的两套命名**，不是两颗芯片。
- 修订：`0x400c0110` 用 vendor mask `0xff00` 或 ath11k mask `0x0f00` 都解出 **major 1 / minor `0x10`**。上游 ath11k 的 WCN6855 分支只收 major 2（会 `-EOPNOTSUPP`）；SteamOS-ARM 的 REDMAGIC 6（同为 SM8350 + QCA6490）补丁把它映射成 `ATH11K_HW_WCN6855_HW21`（`wifi-pack/ref-steamos/0008-qca6490-hw21.patch`）。

**固件为什么用 `amss.bin`、不用 `amss20.bin`：**

- 厂商规则 `cnss2/pci.c:4658` `cnss_pci_update_fw_name()`：`QCA6490_DEVICE_ID` 且 `major_version == 2` → `amss20.bin`（`FW_V2_FILE_NAME`）；其余 → `amss.bin`（`DEFAULT_FW_FILE_NAME`）。
- 本机 major 1 ⇒ 应加载 `amss.bin`。真机 Android 的 dmesg 也是 `amss.bin`（`venus-recon\android\venus-dmesg.txt:758-762`，从 `/vendor/firmware_mnt/image/amss.bin` 取）。
- 因此 `amss20.bin`（hw2.0 镜像，与一加9 同 md5，也躺在本机 `/vendor` 里）在 venus 上停在 EE=1 不是“固件坏了”，是**版本不对**。

## 2. 一轮实验的固定流程（每轮约 5 分钟）

在 WSL 里改代码、编译：

```bash
# 1) 打补丁（每个 replace 都要 assert count==1；新探针编号不能用重复）
wsl -e bash /mnt/c/.../venus-recon/buildNNN.sh     # 内部会跑 applyNNN.py 再 tools/make-kernel.sh
# 判据：errors=0，且 strings hakios-kernel | grep -c apply-NNN 为 1
# 注意：make-kernel.sh 退出码 2 是已知的 kext symbol-set 检查失败，不代表编译失败
```

在 Windows 里打包 + 上机 + 取证：

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force   # 每个新 pwsh 会话都要
$fb='C:\...\default-workspace\tools\platform-tools\fastboot.exe'
wsl -e bash /mnt/c/.../venus-recon/mkNNN.sh          # 打包 p-pNNN.bin，打印 sha256 和 cmdline
& $fb reboot bootloader                              # 冷启动，等 4f9baecb（6–24 s）
cd C:\...\venus-recon
.\run-p104.ps1 -Payload p-pNNN.bin -Tag pNNN -RunSeconds 115
& $fb oem dump logdump 0 40000                       # 立刻返回 OKAY
Start-Sleep 5
& $fb get_staged "C:\...\venus-recon\cur-pNNN.bin"   # 262,144 B
.\extract-log.ps1 -File "C:\...\venus-recon\cur-pNNN.bin" -Out "C:\...\venus-recon\pNNN.txt"
```

### 绝对不要踩的坑（每条都真的废掉过一整轮）

1. **cmdline 只有 514 字符**。loader 自己的前缀占 93 字符，payload cmdline 只装 514；超了从尾部静默截断。**每轮必须确认日志里没有** `WARNING: the kernel command line is TRUNCATED`。
2. **`pcie_tag` 不要写进 EXTRA**：`mk-pcie2.sh` 自己会追加。
3. **必须冷启动**。热启动会得到 LTSSM 3/5 或脏状态。从 Android 侧 `adb reboot bootloader` 中间会掉 USB 很久，`for` 循环要等 ≥180 s。
4. **日志会串轮**：`logdump` 里保留着历史启动。必须先按 `pcie_tag=pNNN` 切片，只取以 `the probe is done…(apply-169)` 结尾的最新那组时间戳。
5. **64 位指针不要存进 `uint32_t`**。偏移量用 `uint32_t`、用时现加：`rd(pcie_dma_extra + off)`。犯过三次，现象是"第一条读之后日志就没了"（loader 的 trap 把 fault 吞掉）。
6. **TRE 的 CPU 地址**：`pcie_dma_extra + (iova - PCIE_EXTRA_IOVA)`。算错会把 ch20 的 TRE 写进 ch21 的上下文。
7. **通道上下文在 `pcie_dma_extra + ch*0x2c`**（ch20 → `0x370`），**没有 +0x2000**；`+0x2000+er*0x2c` 是**事件**上下文，`+0x2400` 是命令上下文。事件**环**在 `+0x4000`（er0）/`+0x5000`（er1）/`+0x6000`（er2）。
8. **"界外指针"要用 `0x80000000`**：MHI 窗口是 `0xa0000000..0xb0000000`，`0xa0100000` 仍在窗内，不产生 fault。
9. **`run-p104.ps1` 要求设备停在 `4f9baecb`（原厂 bootloader）**，若停在我们的 xnuloader，脚本静默失败，后面 `oem dump` 报 `unknown command`。
10. **`ld-pNNN.bin` 和"back in the loader after 30 s"是脚本的假数据**，只有 `cur-pNNN.bin` 是真的。
11. `Set-Content -Encoding UTF8` 会写 BOM+CRLF，WSL 里 `#!/bin/bash` 会报"文件不存在"。`.sh` 用写文件工具生成，或 `sed -i 's/\r$//'`。
12. `wsl -e bash -c "…"` 的引号会被 PowerShell 吃掉（甚至把命令跑到 Windows 侧）。**一律写进 `.sh`，用 `wsl -e bash /mnt/c/.../x.sh`**。
13. `applyNNN.py` 的两个 gate 锚点（`hakios.pcie.c` 约 `:3503` 与 `:4081`）里，`pcie_mhi_data != NNu` 的链条只能追加自己编号，且两处上下文不同（一处后面接 `&& pcie_chanstart != 0`，一处后面是 `)`），**锚点字符串要带后缀才唯一**。

## 3. 已经证实的东西（可以直接当事实用）

### 3.1 上电与链路（M0）
六路 rail 全部投票成功（`ldob6 1200`、`ldob5 880` + 射频六路 `smpb10 1800 / ldoe7 2800 / smpe2 1012 / smpb11 1012 / smpc1 1900 / smpb12 1350`），`CLKREQ#`(95)、`WLAN_EN`(64)、`PERST#`(94)、`BT_EN`(65)、`SW_CTRL`(153) 全部拉好，`link UP: ELBI 0x08 = 0x00011401`、`LTSSM 0x00000111`、Gen2。

### 3.2 固件下载
- BHI：`BHI_IMGADDR 0xa0004000`、`IMGSIZE 0x80000`，`BHI_STATUS = 0x80000001`（SUCCESS + READY）。
- BHIE：10 个向量 × 512 KiB，`TXVECSTATUS = 0xbbd056f0`（top 2 = XFER_COMPL，seq 段与我们写进去的 `0x3bd056f0` 一致），589 ms 完成。
- 下载后设备从 `EE=1`（SBL）进到 `EE=2`（AMSS），`MHISTATUS = 0x201`。

### 3.3 MHI 控制面
`MHICFG 0x00030880`（NCH 128 / NHWCH 3 / NER 3 / NHWER 2）、`CHDBOFF 0x300`、`ERDBOFF 0x700`、`BHIOFF 0x100`、`BHIEOFF 0x224`，上下文区 `CCABAP 0xa0200000`、`ECABAP 0xa0202000`、`CRCBAP 0xa0202400`。er0 上有 boot 期事件：`STATE_CHANGE(state=2)`、`EE_EVENT(ee=2)`、4 条 `CMD_COMPLETION(code=1 SUCCESS)`。

### 3.4 **数据面已通（LOOPBACK）**
p431：给 ch1 铺两个 RX buffer，往 ch0 发 16 字节 ⇒ 事件环收到 ch0 的 `TX_EVENT(0x22)` 和 ch1 的完成事件（`dword3` 低字节 = 通道号），**我们写的字节原样出现在 ch1 的缓冲区里**。
⇒ 主机的 TRE 取用、payload DMA、事件投递全部正确。

### 3.5 事件字段语义
`dword2` 高 16 位 = code/状态，低 16 位 = 长度；`dword3` 的 bit16-23 = 事件类型，**低 8 位 = 通道号**。

### 3.6 通道上下文是**固件自己写的**
关掉 `pcie_chanstart` 后（p468）看到 ch0/ch1/ch20/ch21 全是 `0x00000202`（RUNNING + brstmode 2）、`chtype` 1/2、`erindex 1`、`rbase 0xa0208000/9000/c000/d000`、`len 0x200`，全部由固件在 host 动手之前建立。

### 3.7 只有 `0x202` 能让 AMSS 启动
早期发布 ch20 上下文时改值：`0x202` → EE=2；`0x200`（六条全 0）、`0x200`（只 IPCR）、`0x201` → **EE 恒 1，AMSS 永不启动**。
⇒ 固件在 SBL→AMSS 交接时**确实读这两条通道的上下文**，通道对象存在且被消费。

### 3.8 真机（原厂 Android）成功态
`echo on > /sys/bus/pci/devices/0000:01:00.0/power/control` 然后读 `/sys/kernel/debug/mhi/1103_00:01.00/{states,chan,events,regdump}`：
- 常态 **M2**（`MHI_CNTRL 0x400` / `MHI_STATUS 0x401`），`EE:AMSS`；
- IPCR 两通道 `state 0x3`（SUSPENDED）、`brstmode 0`、`len 0x200`，**但 wp/rp 一直在动** ⇒ QMI/QRTR 真的在跑；
- LOOPBACK 两条**根本没配置**（state 0 / base 0 / len 0）——我们能拿它当对照组，只是因为固件给这两条留了功能。

### 3.9 RDDM
写 `MHI_SOC_RESET_REQ (0xb0) = 1` 能把设备打进 `EE=3`（RDDM，7–20 ms），**再写一次能钉住**；但 BHIE RX 无论下载前武装（p447）还是启动后武装（p438）都收不到任何 dump 字节 ⇒ 这条路拿不到固件 crash 记录。

### 3.10 固件里真的有一套 IPC Router
`amss.bin` 内字符串（vaddr）：

```

0x0160bbba  ipcr_debug_hello_sent_ts_cntr = %d
0x0160bc58  IPCR_CORE_DEBUG     0x0160bc74 IPCR_MHI_TX_DEBUG   0x0160bc92 IPCR_MHI_RX_DEBUG
0x0160bc68  1st message          0x0160bc86 1st Message
0x0160bcb0  In ipc_router_xal_up xport->up = 0x%x,xport->hello_sent = 0x%x
0x0160bcef  In ipc_router_xal_up ..ERROR. xport == NULL

⇒ 固件侧的关口是 **`ipc_router_xal_up()` 有没有拿到 `xport`（传输对象）**，也就是"固件内部的 MHI 客户端有没有把 IPCR 通道挂上去"，而不是主机敲哪个门铃。

### 3.11 `amss.bin` 是 Hexagon（Q6）固件 —— 不是 ARM/Thumb（2026-11-11 核实，**推翻旧假设**）

之前"amss.bin 是 ARM Thumb-2、可用 `arm-none-eabi-objdump` 反汇编"的假设**不成立**：ARM 与 Thumb 两种模式都只解出数据状内容；全文件 `70 47`(bx lr) 仅 113 次 / 5 MB（随机期望 ~76），`10 b5` 25 次，ARM `bx lr` 0 次。

它是 **Hexagon（Q6 DSP）固件**，ELF 头的 `e_machine=40(ARM)` 只是打包默认值。用 LLVM 的 hexagon target 反汇编立刻得到合法代码（WSL 里 `llvm-objdump` 18.1.3 已注册 hexagon）：

```
# 复制并把 offset 0x12 的 e_machine 改成 164 (EM_HEXAGON)，然后：
llvm-objdump -d --triple=hexagon --mcpu=hexagonv66 /tmp/amss_hex.elf > /tmp/amss_hex.dis
# 结果：795,208 行，stderr 为空；0x2000 段首是 jump 表，0x15ede6c 处能读到
#   r0 = ##0x160bcb0   ← "In ipc_router_xal_up xport->up..."
```

已写成脚本：`venus-recon/re-hx-elf.sh <hex-imm-substring>`（反汇编 + grep 常量引用），`re-hx-dump.sh <lo> <hi>`（按 vaddr 导出）。已定位：

- `0x15edd6c` = IPCR debug flag 注册函数：注册 `IPCR_CORE_DEBUG`/`IPCR_MHI_TX_DEBUG`/`IPCR_MHI_RX_DEBUG` 到全局 `0x16d7570/71/72`，日志结构指针在 `0x16d7574`。
- `0x15ede6c` = 打印 `In ipc_router_xal_up xport->up=...` 的函数：`r0` = xport，读 `xport+0x2c`(up) / `+0x2d`(hello_sent)；xport==NULL 走另一条日志；尾部 tail-call `0x839840`。
- `0x15ede64` 是 thunk：`r3=0; jump 0x14c4df0` → 再 `jump 0x8559bc`（debug flag 查询的外部 stub）。

**注意**：`0x8xxxxx`（`0x839840`、`0x8559bc` 等）不在任何 ELF 段内 ⇒ 是 QURT 的对外 stub / 动态符号区，静态分析到 thunk 为止；要继续跟进得先搞清 QURT 的 stub 解析机制，或只从 `0x14c4000`/`0x170d000` 段内的调用者往下走。

教训：**以后所有 amss.bin 静态分析用 Hexagon，不要再用 Thumb/ARM。**

**静态分析边界（2026-11-11 追加）**：`0x15ede6c`（xal_up）在整个 5 MB 镜像里**没有任何 4 字节函数指针引用，也没有任何 direct call/jump**——它只被自己引用（尾部 tail-call `0x839840`）。`0x15edd6c`（IPCR debug 注册）**只在 `0x1472940` 的函数表里出现一次**（表项 `0x1472960`，旁边是 QURT 的 `0x83bf44`）——即固件 ELF 只导出了 IPCR 的 **debug 注册回调**，**没有导出 open/up 入口**。`mhi_channel_rw_multiple`（0x15e96f0 起）确认：channel 结构 state 在 `r18+0x10`，**open 状态值 = 2**；`r18==0` → "wasn't opened"；channel 表在 `memw(0x140e154)+0x200`，表大小在 `+0x14`。⇒ **IPCR 的 MHI 传输初始化、channel open 的调用方都在 QURT 镜像（0x8xxxxx）里，ELF 里只有被调用的接口函数，静态分析到这里是硬边界。**

### 3.12 命令环时序：M0 必须在 READY 时写（2026-11-11 晚追加）

**star 金标准（`venus-recon/wifi-pack/ref-star/source/hackios-xnu-kernel/xnu/files/bsd/dev/lemonade_wifi.c`）**：`mhi_ready()` 在 **EE=1（READY）** 时完成全部 MHI 初始化并写 M0；`ipcr_probe()` 在 **EE=2（mission）之后** 发 START_CHAN(20/21)，`ipcr_start_command()` 拿到 completion code 1。⇒ **命令环在稳态可用，不是"只在 boot 窗口"**。

star 的 `mhi_ready()` 序列（可直接照抄）：
1. 前置：EE=1、`MHISTATUS.READY=1`、RESET=0；
2. 读 CHDBOFF(0x18)/ERDBOFF(0x20)；
3. 通道上下文：ch20 type=1/index=1、ch21 type=2/index=1，base/rp/wp 全 0（disabled，START 前不填）；
4. 事件环 ×3：base=IOVA+offset、len=count*16、rp=base、wp=base+(count-1)*16；
5. 命令环：base=IOVA+0x3400、len=32*16、rp=wp=base；
6. `wake db = channel_db + 127*8` 写 0；
7. `CCABAP=0xa0200000`、`ECABAP=0xa0200800`、`CRCBAP=0xa0200c00`；
8. `MHICFG` NER=3（`(cfg & 0xffff) | (3<<16)`）；
9. `MHICTRLBASE=DATABASE=0xa0000000`、`LIMIT=0xb0000000`；
10. 敲 3 个事件环门铃（er db）；
11. **写 M0**：`0x38` 的 bit8-15 = 2（即 `2<<8`）；
12. `wake db = 1`；轮询 `MHISTATUS` state==2 且收到 m0_seen 事件。

**p476 的失败根因**：cmdline 用了 `pcie_mhi_nom0=1 pcie_mhi_late0=1` —— **跳过 READY 时的 M0，等 EE=2 之后才补写**（日志 `apply-270 m0 skipped`、`apply-286 m0 after mission`）。顺序与 star/vendor 相反，于是 AMSS 启动后 MHI 引擎虽报 `MHISTATUS=0x201`，命令环却不取 TRE、不回 completion，也不崩。**CONTINUE「更正 1」的 "boot 窗口" 结论应重新理解为 "M0 早写的窗口"**——不是 "EE=2 之后永远无效"（star 的 EE=2 后 START 成功就是反证）。

**下一轮实验（apply-477）**：p476 参数只改两个——`pcie_mhi_nom0=0 pcie_mhi_late0=0`，其余（`starflow=1 pcie_mhi_data=50 pcie_chanstart=0`）不变；starflow 的 START_CHAN 逻辑保留（star 证明 EE=2 后发没问题）。预期：apply-286 那行变成 "m0 early/ready"，er0 出现 type=0x21、d0==0xa0207000/0xa0207010 的新 completion，ch20/21 变 0x202 并保持；若仍无 completion，再查 ECABAP/CRCBAP 是否该从 p476 的 0x2000/0x2400 改回 star 的 0x800/0xc00。

**capability 配置不是缺失项**：venus 只 advertise 一个 capability——`MISC(0x24)=0xa20`，`cap[0] id 3 (BW_SCALE), next 0`，cfg4 已是 `0xfd100000`（apply-324，er 2）；无 TIMESYNC。

**IPCR 客户端 open 仍待确认**：`mhi_channel_rw_multiple` 要求 channel state==2（OPEN）；START 成功后设备应把 ch20/21 置 RUNNING，但 AMSS 的 IPCR 客户端（QURT 0x8xxxxx）是否消费 TRE，要看 apply-477 的 er 事件与数据环。`ipc_router_xal_up` 在 ELF 里零引用，静态到此为止。

### 3.13 p477 实测：M0 在 EE=1 写会 SYS_ERR；晚写 M0 时命令环可用（2026-11-11 晚）

`ld-p477.bin` 里有两段 boot 日志（logdump 保留了上一轮），必须分开读：

- **181 s 段 = 本轮 p477**（`nom0=0 late0=0`，`mk477.sh`）：`apply-251` EE=1 mh=0x101 → `apply-277 mhicfg 0x02030880 -> 0x00030880` → **`apply-273 m0 fault check: fsr 0x00000400 far 0x00000050:52be883a mh 0x0000ff05 ee 0x00000001`** → `apply-264 after m0 mh 0xff05` → `apply-252 done ee 3 mh 0xff05`。⇒ **nom0=0 让 M0 在 EE=1 写，立刻 SYS_ERR 0xff05，整轮崩**（与 p475 的 earlym0 一致）。**M0 绝不能早写**。
- **105 s 段 = 上一轮**（`nom0=1 late0=1` + 同一新 kernel，不是 p477）：`apply-270 m0 skipped`（mh 0x101）→ apply-265 在 EE 1→2 窗口发 START_CHAN(0/1/20/21)（t=35 ms ee 0x2 mh 0x101）→ **`apply-286 m0 after mission: mh 0x00000201`**（无 SYS_ERR）→ `apply-282` 稳态再发 4 条 START_CHAN(0/1/20/21) → **事件环 4 条 CMD_COMPLETION（type 0x21）code 1**，d0 = 0xa0207000/0x7010/0x7020/0x7030 → `apply-294 ch20[00] 00000002 00000001 00000001 a020c000`（chstate=2 RUNNING，ch21 同）→ `apply-322 rx primed 32`（ch21 rp 0xa020d000 wp 0xa020d200）→ `apply-292 send: tre ptr 0xa020e000 len 0x1000` → `apply-317 rang again: ch20 rp 0xa020c000 wp 0xa020c020 mh 0x201`（**rp 不动**）→ `apply-297 fsr 0x400 far 0x25012ba883a`（EE=2 稳定）→ `apply-327 tail ... ee 3 mh 0xff05`（末尾二次写 ch20=0xa0208000 环导致，与本轮结论无关）。
- **结论**：M0 必须晚写（EE=2 后，apply-286 路径）；晚写后命令环稳态可用（4 条 completion code 1 + ch20/21 RUNNING）；**数据面仍零消费**（ch20 TX rp 不动、ch21 RX rp 不动），设备侧 IPCR MHI 客户端没读环。p476 的"无 completion"是旧 kernel/时序，不是引擎限制。
- SMMU：apply-273/297 打印 `fsr 0x00000400 far 0x25012ba883a`（p475 也有 `fsr 0x400 far 0x5012be883a`），EE=2 下稳定不崩。
- **下一步 p478**：参数回到 `nom0=1 late0=1`（p476 那套）+ 当前新 kernel；在 START_CHAN completion 后：(1) 等 ≥10 s；(2) 按 star 发 QRTR hello（2 字节 {2,{0}} 到 QRTR_CONTROL_PORT/0xffffffff）再敲 ch21 db；(3) 再发 TX TRE 观察 ch20 rp；(4) 若仍不动，对比 star 的 IOVA 布局（rbase 0x3600/0x3800 vs 0xc000/0xd000）与 ER 数量。

### 3.14 p479–p481：命令环能通、数据环零消费——设备自己把 ch20/21 置 RUNNING 也不读 TRE（2026-11-11 晚）

- **p479**（`apply-479`：在 apply-430 前补写 cmd ctx 的 rbase/rlen = 0xa0207000/0x1000）：`ld-p479.bin` 里 `apply-430 ctx: ch20 0x201 rbase 0xa0203600 …`，`start20/start21: no completion in 3 s` 依旧；`t=1..10 s ch20 rp 0xa0203600 wp 0xa0203610` 不动。⇒ 只补 rbase/rlen 不够；单条 TRE + 单独门铃（0x7010/0x7020）这条路不行。
- **p480**（`pcie_chanstart=1 pcie_starflow=0 pcie_mhi_data=53`，走 apply-265/apply-289/apply-286/apply-308/apply-282 老路径）：`apply-282 chstart tre 00120000 01120000 14120000 15120000 cc wp 0xa0207040` 之后，`apply-293 ev[20..50]` 出现 **4 条 CMD_COMPLETION（d0 = 0xa0207000/7010/7020/7030，type 0x21，code 1）**，ch20 变 0x202；但 `apply-292 send`（ch20 TX TRE）后 `ch20 rp 0xa020c000`、`ch21 rp 0xa020d000` 都不动；本轮自己结束时 `apply-327 tail … ee 2 mh 0x201`（**健康**）。
  - **更正**：`ld-p480.bin` 里 112.7 s 的 `tail ee 3 mh 0xff05` 属于 logdump 里残留的**旧 boot**（apply-404 块，门控 `pcie_mhi_data==25`），不是 p480 崩溃；p480 没有崩。
  - 结论：**一次写 4 条 TRE + cc wp 直接到 0x7040 + 单次门铃 0x7040** 能让命令环被消费并回 completion；单条 TRE/逐步门铃（apply-430）不行。差别在批量与 wp 语义，不在 rbase/rlen。
- **p481**（`chanstart=0 late0=1 nom0=1 mhi_data=54`，新增 apply-481：**完全不碰** ch20/21 上下文，只在设备自己的环上写 hello TX TRE 与 32 条 RX TRE、更新 wp、敲 ch20 0x3a0 / ch21 0x3a8）：`apply-481 a: ch20 st 0x202 rbase 0xa020c000 rp/wp 0xa020c000 | ch21 st 0x202 rbase 0xa020d000 rp/wp 0xa020d000` —— **设备自己把两条通道置为 RUNNING（0x202）并给定了环**。写入后 10 s 采样：`ch20 rp 0xa020c000 wp 0xa020c010 / ch21 rp 0xa020d000 wp 0xa020d200`，**rp 一格没动**；EE=2、mh=0x201 稳定不崩。
  - 结论：**即便通道是设备自己开的、环是设备自己的、TRE 与门铃格式都正确，固件侧也没有任何消费者读数据环**。主机侧环设置、M0 时序、上下文写法全部排除；只剩固件 IPCR 客户端未 attach（与静态分析 `ipc_router_xal_up` 零引用一致）。
- **下一步建议**：转 §7 路线 B（star 现场日志逐帧对比）或 C（QRTR-over-MHI 上层）。路线 A 的主机侧参数试错已无信息量。

### 3.15 真机 vendor MHI 日志：IPCR 在 START 后毫秒级就通；我们唯一的差异是「早 M0」写不进去（2026-11-11 晚）

- 素材：`android/cnss-mhi-clean.log`（74 KB）、`cnss-mhi.log`（150 KB）、`cnss-mhi-cntrl.log`（14 KB），是 macOS/Windows 侧从真机抓的 vendor cnss2 MHI 日志；编码是 **UTF-16LE BOM + ASCII 正文**，用 `[IO.File]::ReadAllBytes` 跳过前 2 字节后按 ASCII 解码可读（`Get-Content -Encoding Unicode` 会乱码）。已转出 `cnss-mhi-clean.txt`、`cnss-mhi.txt`、`cnss-mhi-cntrl-u8.txt`。
- **真机时序（Android，31.5–32.21 s）**：
  1. `mhi_alloc_bhie_table Allocating bytes:5236304 seg_size:524288 total_seg:11` —— 就是 venus 的 `amss.bin`（5,236,304 B = 9×524,288 + 517,712，所以是 10 个数据段 + 1 个 160 B 的 **BHI 向量表**段）。
  2. `mhi_firmware_copy Setting Vector:0xa0700000/…/0xa0b80000 size:524288`（10 条），向量表放 host 内存 0xa0700000 起。
  3. 31.536 `Processing Event:0x17103f800003000 0x02000000 0x00200000` → `MHI state change event to state:M0` → `mhi_pm_m0_transition Entered With State:READY`；紧接 `EE received event:SBL`。**即：vendor 在 EE=1（SBL）时就写 M0，而且不崩。**
  4. 32.190 `device ee:AMSS dev_state:M0`；32.192 `mhi_prepare_channel Entered: preparing channel:20` → `mhi_send_cmd WP:0xa0108000 TRE: 0x0 0x00000000 0x14120000`（**单条** START_CHAN(20)）→ 32.194 `Processing Event:0xa0108000 0x01000000 0x00210000` → `Chan:20 successfully moved to start state`。
  5. 同一毫秒 `mhi_queue_skb chan:20 WP:0xa0c01000 TRE:0xa0c02a00 0x00000034 0x00020200`（**首发 52 B QMI**）；随后 prepare ch21 + START `WP:0xa0108010 0x15120000`，再布 32 条 RX TRE（WP 0xa0c03000 起、TRE 0xa0c08000 起、len 0x8000、flags 0x00020200）。
  6. 32.207 起数据事件环（`er_index:1`）立刻工作：`Processing Event:0xa0c01060 0x02000034 0x14220000` = ch20 的 **TX_EVENT(type 0x22)**，host 收一个补一个 `mhi_queue_skb`；ch21 侧事件 `0x02000034 0x15220000`，host 补 `mhi_gen_tre`。⇒ 真机上 **START 完成后毫秒级** IPCR 双向就跑起来了。
  7. 地址布局：ctrl 段约 0xa0100000（cmd ring 0xa0108000）、data 段约 0xa0c00000（ch20 ring 0xa0c01000、ch21 ring 0xa0c03000、RX 缓冲 0xa0c08000 起）、固件 staging 0xa0700000。
- 对我们的意义：主机侧「单条 TRE + 单独门铃」在真机上也是这么发的（`mhi_send_cmd` 就是单条），所以 p479 的失败不是批量/单条语义问题；真机与我们的**唯一结构差异是「EE=1 时写 M0」**——vendor 能写成，我们写就 0xff05。
- **p482**（`chanstart=1 starflow=0 mhi_data=53 chzero=2`，boot 期 ch20/21 预发布 disabled 0x200）：`apply-299 … ch20 0x200 ch21 0x200` 生效；apply-282 4 条 TRE 仍拿 4 条 completion code 1，ch20 → 0x202；但数据面块（apply-478）在 starflow 分支里没执行（`apply-478` 0 次、`apply-430` 9 次），所以**没测到数据消费**。
- **p483**（`nom0=0 late0=0 starflow=1 chzero=2 mhi_data=0`，SMMU 未启用）：`apply-264 after m0: mh 0x101 ee 1 ctrl 0x0` —— M0 写进去没落地、也没崩；只是 SMMU 关时寄存器写被吞，不算数。
- **p484**（`p480 参数 + nom0=0 late0=0 chzero=2`，SMMU 起）：`apply-273 m0 fault check: fsr 0x400 far 0x250:12be883a gfsr 0 mh 0xff05 ee 1`；`apply-264 after m0: mh 0xff05 ee 1 ctrl 0x200`；之后 EE 到 2 但 MHI 恒 0xff05，START 全无 completion。⇒ **chzero=2 救不了早 M0；EE=1 写 M0 在 venus 上必 SYS_ERR**（p477/p484 两次复现；far 值与 p477 的 `0x50:52be883a` 不同，都是垃圾）。
- 尚未复现的 vendor 结构差异（按可疑度）：
  1. **早 M0 写不进去**（vendor 在 READY 写 M0 是标准流程；我们写就 SYS_ERR，M0 值 `(ctrl & ~0xff00)|(2<<8)` 与 vendor 一致）。
  2. **固件装载方式**：我们 `pcie_novec=1`，`apply-239: bhie registers left untouched`，走 BHI 数据窗口（0xa0004000/0x80000）推 10 段；vendor 是 BHI vector 方式（host 建 11 条向量表、设备来拉）。若设备对「push 进来的镜像」校验/布局与 pull 方式不同，早 M0 时跳转地址可能不同。
  3. 窗口：我们用 0xa0200000–0xa0a00000（8 MB），vendor ctrl/data 在 0xa0100000/0xa0c00000。
- 建议下一轮（p485）：**先只测「早 M0 + 延迟」**（READY 后等 500 ms 再写 M0，其余同 p484）；若仍崩，改 `pcie_novec=0` 走 BHIE 向量路径再试早 M0。两条都失败再考虑 §7 C。

### 3.16 p485–p487 三个否定实验：早 M0 的 SYS_ERR 与时机、装载方式都无关（2026-11-11 晚）

- **p485**（`p484 + pcie_m0_now=1`：在 READY 轮询循环里**第一次看到 EE=1 的同一毫秒**写 M0，比 vendor 还快）：`apply-485 m0 at first ee1: ctrl 0x0 -> 0x200 mh 0x101`，21 ms 后 `apply-273 … mh 0xff05`、`apply-264 after m0: mh 0xff05 ee 1`。⇒ **不是时机问题**：EE=1 写 M0 无论多早都 SYS_ERR。
- 补丁：`p485-patch.py`（新增 `pcie_m0_now` 开关，插入 READY 循环内，写一次即清零）；内核 10:30:20 重链、含 apply-485；`p485` 内核已装到 `/root/hakios/hakios-kernel`。
- **p486**（`nom0=1 late0=0 ee2m0=1 chzero=2`：**EE 变成 2 的瞬间 1 ms 内**写 M0）：`apply-362 m0 the moment ee 2 showed: mh 0x201 ctrl 0x200 after 1 ms` —— M0 被接受、状态健康；随后 apply-282 四条 START 仍回 4 条 completion、ch20 → 0x02；但 `apply-293 final … ch20rp 0xa020c000 ch20wp 0xa020c010`，**ch20 TX TRE 的 rp 一格没动**。⇒ M0 在 EE=2 后 1 ms 内写也**不能**让 IPCR 客户端 attach。
- **p487**（`p484 + pcie_novec=0`，走 BHIE 向量寄存器、让设备自己来拉镜像）：`apply-222: 10 vectors ready` 后依旧 `apply-273 … mh 0xff05`。⇒ **装载方式（push 窗口 vs BHIE 拉取）也不是早 M0 崩的原因**。
- 三个实验合起来的结论：早 M0 的 SYS_ERR 是设备侧对「SBL 阶段收到 M0」的确定性反应（不是竞态、不是镜像装载路径）；而晚 M0（EE=2 后任意时刻）MHI 状态健康但 IPCR 客户端永远不 attach。
- 还剩两条路：
  1. **抓 RDDM 崩溃转储**看 AMSS 到底异常在哪（vendor 驱动支持 RDDM，固件里有 `mhi_core_tgt_config_rddm`；我们的 apply-345 把 RDDM 块编译掉了，需要重新打开）。这是唯一能直接看到设备侧异常 PC 的办法。
  2. **验证 AMSS 是否真的在跑我们下载的镜像**：故意破坏镜像（改一个字节/截断），看 EE=2 是否照常出现。若照常，说明设备跑的是 flash 里的 AMSS，我们的 BHI 下载根本没被使用——那么「客户端不 attach」的解释就要换成设备侧配置而不是镜像。

## 4. 当前失败边界（准确描述）

AMSS 起来之后（EE=2、MHISTATUS=0x201）：

| 主机动作 | 结果 |
|---|---|
| 敲通道门铃（ch20 `0x3a0`，值 = ring wp） | 无反应，不取 TRE，`rp` 不动 |

| 追平事件环 `ctxt.wp` 再敲事件门铃 | 无反应 |
| 只读观察 10 s / 100 ms 采样 | 零变化（不是"起得慢"） |
| 在 EE=1（SBL）请求 M0 | **立刻 SYS_ERR**，整轮作废 |
| 早期发布 `chstate 0`/`1` | AMSS 不再启动 |

0x98/0x9c MHIDATABASE_H/L  0xa0/0xa4 MHIDATALIMIT_H/L  0xb0 MHI_SOC_RESET_REQ  0x128 EE
0x6f0 BW scale DB  0x6f8 wake DB  0x700+er*8 事件门铃  0x300+ch*8 通道门铃
```
`MHICTRL`：状态在 bit8-15（M0=2<<8、M2=4<<8），RESET 在 bit1。
`MHISTATUS`：状态 bit8-15、`SYSERR 0x4`、`READY 0x1`。

### BHI（在 BHIOFF=0x100 处，**不是 0x224**）
`0x00/0x04 ver`、`0x08/0x0c IMGADDR`、`0x10 IMGSIZE`、`0x18 IMGTXDB`、`0x20 INTVEC`、`0x28 EXECENV`、`0x2c STATUS`（top2：0 RESET / 2 SUCCESS / 3 ERROR）、`0x30 ERRCODE`、`0x34/0x38/0x3c ERRDBG`、`0x40 SERIALNU`、`0x48 NUMSEG`。

### BHIE（在 BHIEOFF=0x224 处）
`TX：0x2c/0x30 ADDR、0x34 SIZE、0x3c DB、0x44 STATUS`；`RX：0x60/0x64 ADDR、0x68 SIZE、0x70 DB、0x78 STATUS`。

### 上下文结构（stride `0x2c`）
`+0x00 chstate:8 / brstmode:2 / pollcfg:6 / rsvd:16`、`+0x04 chtype`、`+0x08 erindex`、`+0x0c rbase(64)`、`+0x14 rlen`、`+0x1c rp`、`+0x24 wp`。
通道 `ch*0x2c`；事件 `0x2000 + er*0x2c`；命令 `0x2400`。

### 环与 payload
事件环 `+0x4000/0x5000/0x6000`，命令环 `+0x7000`，数据环 `0x8000 + didx*0x1000`（didx 0..5 对应 ch 0,1,4,5,20,21）。

### 一轮的 payload 参数（p476 用的那套，无截断）
```
pcie=1 pcie_step=5 pcie_power=1 pcie_delay=0 pcie_settle=100 pcie_bar=21 pcie_watch=0
pcie_star_mask=31 pcie_bhi_addr=0xa0004000 pcie_bhi_size=0x80000 pcie_novec=1 pcie_msi_test=1
pcie_mhi_nom0=1 pcie_chanstart=0 pcie_mhi_late0=1 pcie_mhi_data=NN pcie_starflow=1
```
`pcie_mhi_data` 是"跑哪一段探针"的开关；**注意：它在 BHI 握手时还没解析出来（读到 0）**，早期探针若用它做 gate 需要就地 `PE_parse_boot_argn`。

## 7. 接下来可以走的路（按性价比）

**A. 反编译 `amss.bin`（推荐，唯一能拿到"为什么"的路）**
**已推翻旧假设：amss.bin 是 Hexagon（Q6）固件，不是 Thumb-2**（见 §3.11）。工具链：WSL 的 LLVM 18.1.3（`llvm-objdump`/`llvm-mc` 已注册 hexagon target）；把 ELF 头 `e_machine` 从 40 改成 164 后 `llvm-objdump -d --triple=hexagon --mcpu=hexagonv66` 即可全量反汇编（795K 行，零错误）。现成脚本 `re-hx-elf.sh` / `re-hx-dump.sh`。
入口线索：`ipc_router_xal_up` 的格式串 `0x0160bcb0` / `0x0160bcef` 已被 `0x15ede6c` 引用（xport->up/hello_sent 日志）；`0x15edd6c` 是 IPCR debug 注册函数；`1st message`(0x160bc68) 在 `0x15edd6c`-`0x15ede64` 这段里。下一步：从 `0x15edc00`-`0x15ede60` 这块（MHI 传输层）往上找 xport 创建，或追 `0x16d7574` 全局的写入者。
注意：`0x8xxxxx` 地址（如 `0x839840`、`0x8559bc`）不在任何 ELF 段内，是 QURT 对外 stub，静态分析在 thunk 处断开。
目标问题：**谁创建 `xport`？创建条件是什么？**（大概率是"主机发来第一条 MHI 消息"或"通道 open 完成回调"——如果是后者，就是死锁，需要换思路）

**2026-11-11 晚更新：A 已到边界。** 上面三个入口都追完了：xal_up 无引用、debug 注册只在 `0x1472940` 表、数据面检查在 `mhi_channel_rw_multiple`（state=+0x10, open=2）。**IPCR 的初始化/通道 open 逻辑不在 ELF（QURT 镜像内）**，继续啃 ELF 没有增量。建议转 **B（star 日志）或 C（QRTR-over-MHI 上层）**；若坚持查固件，得先解决 QURT stub 解析（0x8xxxxx 的符号表/ROM 镜像）。

**更进一步（见 §3.12）：star 金标准证明命令环稳态可用，p476 的 `nom0=1 late0=1` 把 M0 写晚了才是根因。** A 的下一步不是再反汇编，而是复现 star 的 `mhi_ready()` 序列（EE=1 时配好上下文/事件环/命令环并写 M0，EE=2 后发 START_CHAN）：**apply-477 = p476 参数改 `nom0=0 late0=0`**，预期拿到 completion code 1、ch20/21 保持 0x202；若仍无 completion，再把 ECABAP/CRCBAP 从 0x2000/0x2400 改回 star 的 0x800/0xc00 再试。

**B. 拿到一台 star（小米 11 Ultra）的现场**
star 用同一份固件跑通了 IPCR。若能拿到它的完整 MHI 侧日志（需要开 MHI_VERB 的内核），可以直接 diff 出"它在 M0 之后我们还差哪一步"。当前手边没有这类日志。

**C. 把 M9 挂起，转做不依赖 IPCR 的上层（风险最低，但不会让 Wi-Fi 可用）**
- QRTR-over-MHI 客户端（`hakios.qmi.c` 里已有 QRTR 结构与 `AF_QIPCRTR` 助手，只需把传输层指向 MHI）
- WLFW 服务层（`wlan_firmware_service_v01.{c,h}` 已在树里）
- ath11k 骨架（`tools/mk-ath11k.sh` 能编出 `out/ath11k.o`）
- Apple80211/IO80211 那一层**已经写好了**：`bsd/dev/hakios.apple80211.c`（29 KB，`SIOCSA80211 0x802869c8`/`SIOCGA80211 0xc02869c9`、ASSOCIATE=20、事件 class 6/subclass 1）、`iokit/Kernel/hakios.wlan.cpp`（发布 `IO80211Controller` 与 `IO80211InterfaceRole="Infrastructure"`）、`bsd/sys/hakios.sta.h`（`struct hakios_sta_ops {scan, heard, join, state, channels}`）
⇒ 一旦 IPCR 通，上层只差"把 QCA6490 的 802.11 实现挂到 `hakios_sta_ops`"。

**D. 换路线（如果目标只是"这台机器能上网"）**
USB 网卡（要 XNU USB host 栈 + 驱动）或蓝牙/USB tether，完全绕开 M9。

## 9. 给接手者的行为约定

1. **每轮只改一个变量**，并且先确认这一轮真的生效（无 TRUNCATED、`apply-NNN` 出现在日志里、`pcie_tag` 对得上）。
2. **不要相信"设备静默"就等于"设备收到但忽略"**——本项目栽过两次：一次是读错了事件环偏移，一次是心跳完成事件其实是 boot 期留下的。判据要带正对照（ch0/LOOPBACK 是已知可用的对照组）。
3. **改动前先备份**：`/root/root.apfs.bak`、`/root/amss-orig.bin` 已存在。
4. **不要热启动**，不要从 Android 侧频繁重启（会掉 USB 数分钟）。
5. 涉及固件内部的问题，**优先静态分析，不要再消耗设备轮次**——设备侧能观察的量已经被榨干。
