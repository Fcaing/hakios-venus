## 本轮新增事实

### p418（apply-377）：0xb0 是活的

`apply-377 t0: ee 0x00000002 mh 0x00000201 ctrl 0x00000200 b0 0xdee3b644 …`（0xb0 写前读回是总线噪声）→ `wr(0xb0, 1)` → `b0 got 1: b0 0x00000001` → **`t=20 ms: ee 0x00000003`**，`socid 0x400c0110` 全程不变（不是整颗 SoC 复位，是固件进 RDDM）。

### p419（apply-378）：1 ms 时间线 + 复位后重敲门铃

- `t0 … evts 6 ch20 st 0x00000000 … cmd rp 0xa0207000 wp 0xa0207040`
- `b0 got 1: b0 0x00000001 ee 0x00000002`
- `t=1 ms: ee 2` → **`t=9 ms: ee 3`**；
- `timeline: changes 2 t_rddm 9 ms t_back 0 ms end ee 0x00000003`（3 s 内没回来）
- 之后 3.7 s 仍 `ee 0x00000003`；`mh 0x00000201 ctrl 0x00000200` 不变 ⇒ **RDDM 下 MHI core 仍宣称 M0，但什么也不做**。
- `cmd redrive: db 0xa0207040 rp before 0xa0207000` → `cmd rp did not move in 300 ms` ⇒ 进 RDDM 之后命令环照样没人消费。
- `end: evts 6 … er[0] 0140e4f4 0140e4f4 a0207000 a0207010 | er[4] a0207020 a0207030 …`：事件环里的 6 条 TRE 内容和 p416 不一样（后面四条头 4 字节是 0xa0207000/10/20/30，正好是命令环四个 TRE 的 IOVA），下一轮要把每条 TRE 的 16 字节完整打出来再判断。

## p420/p421（09:00 之后，这一轮真正翻案的两把）

### p420（apply-379）：事件环里那四条到底是什么

`cmdline: 599 of 607`、无 TRUNCATED。完整 16 字节 TRE 打出来以后：

```
er0[0] 0140e4f4 00899183 02000000 00200000   ← STATE_CHANGE，state 2（dword3 的 16-23 位 = 0x20）
er0[1] 0140e4f4 00899183 02000000 00400000   ← EE_EVENT，EE 2（0x40）
er0[2] a0207000 00000000 01000000 00210000   ← CMD_COMPLETION，code 1 = SUCCESS（0x21）
er0[3] a0207010 00000000 01000000 00210000
er0[4] a0207020 00000000 01000000 00210000
er0[5] a0207030 00000000 01000000 00210000
er0[6..] 全零
smmu: gfsr 0x00000000 cbfsr 0x00000400 far 0x0000025012be883a（cbfsr 从开机就有，和本轮无关）
```

**事件类型在 dword3 的 bit16-23，状态/EE 在 dword2 的 bit16-23**（之前按 dword0>>24 读是错的）。

四条 completion 的 ptr 正好是我们写的四个命令 TRE（0xa0207000/10/20/30），code 全是 1 = SUCCESS。
vendor `mhi_main.c:1119 mhi_process_cmd_completion()` 是拿 **命令 TRE 本身**的 `MHI_TRE_GET_CMD_CHID(cmd_pkt)`
取通道号，事件里的通道字段根本不看 ⇒ 我之前盯着事件 dword1 说"通道号是 0"是白担心。

关键更正：**命令环的 rp 是主机自己维护的，设备从来不写它**（vendor 的 `mhi_pm_m0_transition` 里
`if (mhi_cmd->ring.rp != mhi_cmd->ring.wp)` 用的是主机的 rp）。所以"cmd rp 不动 ⇒ 设备没消费命令"
这条从 p416 一直用到 p419 的判据**是错的**：设备其实消费了，还回了 SUCCESS。

### p421（apply-380）：把事件环擦干净，只发一条 START_CHAN(20)

```
apply-380 before: ee 2 cmd rp 0xa0207000 wp 0xa0207040 er rp 0xa0204060 wp 0xa0204000
apply-380 wiped: tre 00000000 00000000 00000000 14120000 ctxt rp 0xa0207000 wp 0xa0207010
```

`mh 0x0000ff05` = MHISTATE 0xff + SYSERR(bit2) + READY(bit0)，EE 从 2 掉到 3。
也就是说：**命令门铃 0x70 设备是看的、命令环是读的，而且它会校验**（我把 wp 往回拨到 0x7010、
rp 拨回 0x7000，它立刻 SYS_ERR 进 RDDM，没回事件）。这同时证明 p420 那四条 completion 不是格式错的
命令——格式错的话早就 SYS_ERR 了。

1. 我们这边（上下文、ring、TRE、门铃、事件解析）全部正确，不需要再怀疑。

### 由此收敛出的新怀疑：**WLAN 子系统的时钟**
电力六路 rail 都投上了，但**时钟**从未验证。MHI 引擎在 always-on 域里，没 WLAN 时钟也能跑；WLAN 服务（IPCR/qrtr）要 GCC 的 WLAN RCG/RBC 时钟才会初始化。这能同时解释"引擎活、应用层死"和"BHI/BHIE 全成功"。下一步就去查 GCC 里 WLAN 相关的时钟与复位位，并在上电阶段打开它们。

### p450（apply-405，data=26）：五步隔离，锁定 START_CHAN(20)

`mh 0x0000ff05` = MHISTATE 0xff + **SYSERR(bit2)** + READY(bit0)。er0 里那四条是历史事件（STATE_CHANGE state2、EE_EVENT ee2、两条 CMD_COMPLETION code 1），不是本轮的。

### p451（apply-406，data=27）：不改上下文，只发 START_CHAN —— 照样 SYS_ERR
```

apply-406 c: tre at 0xa20c000 -> payload 0xa3a0000, wp 0xa020c010
```

**EE 保住 2，但 MHISTATUS 立刻变 0xff05**：START_CHAN(20) 一发，MHI 就报 SYS_ERR，通道照样不取 TRE。

### 结论（重要转折）
1. **START_CHAN 是毒药**：只要发 START_CHAN(20)，无论上下文是我们的还是固件原来的，立刻 `MHISTATUS 0xff05`（SYS_ERR）。之前 p265/apply-336 时代"START_CHAN 成功并回 SUCCESS"的结论**是历史事件造成的误判**，作废。
2. 这解释了一直以来的怪现象：**通道在 SBL→AMSS 交接时就已经是 RUNNING 了**（`st 0x00000002`，我们从来没让它进过这个状态），我们再发 START 属于重复 START，协议违规 → 固件 assert。
3. 但"通道已经是 RUNNING 却不取 TRE"这件事仍然没解释 —— 说明固件侧的 IPCR consumer 确实没挂，通道是个空转的 RUNNING。
4. 下一轮该走 **RESET_CHAN(0x10) → 等 st 归 0 → 再 START_CHAN** 这条合法路径，让固件重新建立通道；如果 RESET 之后再 START 能回 SUCCESS 且通道真的开始取 TRE，IPCR 就活了。

### p452（apply-407，data=28）：RESET_CHAN 也毒 —— 不是"重复 START"，是"ch20 对象不存在"
```
apply-407 a: ee 2 mh 0x201 ch20 0x00000002 ch21 0x00000202 rbase 0xa020c000
apply-407 b: RESET_CHAN(20) rung at 0xa0207050
apply-407 c: after reset 300 ms ch20 0x00000002 ee 0x00000003 mh 0x0000ff05   ← RESET 也崩
apply-407 d: START_CHAN(20) rung at 0xa0207060

apply-407 g: waited 0 ms ch20 0x00000002 rp 0xa020c000 wp 0xa020c010 ee 3 mh 0xff05
apply-407 j: bhi status 0x80000001 errcode 0x0004161d
```
**RESET_CHAN(0x10) 与 START_CHAN(0x12) 一样，一发就把固件打成 SYS_ERR（EE=3, mh=0xff05）。**

⇒ 最终结论（比"没客户端"更硬）：**固件里 ch20 的 MHI 通道对象根本没被创建**。任何针对它的命令（reset / start / 数据门铃后的取环）都会让固件 assert 进 RDDM。这也反过来解释了 p429–p436 的所有"静默"：不是固件忽略，而是它压根没有这个通道的控制块。

## p477 / p478（apply-431、432）：把 chstate 提前写成 0（star 的写法）⇒ **AMSS 根本起不来**

试的就是上面那条差别。`apply-431` 加 boot-arg `pcie_chzero=1`，把早期发布上下文时的 word0 从 `0x0202` 改成 `0x0200`（chstate 0 = disabled，brstmode 2），其余照 star。

- p478（`apply-432` 加了"等 EE=2 最多 3 s"的护栏，`p-p478.bin` sha256 `ceddb3cb7012129c0a073b0e3270199381c22d1748403599dd8685624e4baa98`）：

⇒ **context word0 写成 chstate 0 会让 AMSS 永远不启动**（EE 一直 1、MHISTATUS 0x101、er0 全零）。对照 p476（`0x202`）那一轮末尾是 `ee 0x00000002`。
