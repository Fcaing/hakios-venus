# 交接：Xiaomi Mi 11（venus）HakiOS 移植 — 2026-11-08 → 11-10

> 读这份就够了。上一份 `HANDOVER-2026-11-08.md` 里"M4 卡在 PBL 不跳转"的结论**已被推翻**：那时真正缺的是 MSI 使能位的一个 bit。M4/M5/M6/M7 现在全部实测通过，卡在 M8（数据面）。

## 一句话状态

**固件链路全通**：PBL 收下 BHI 前缀 → 跳 SBL → 主机 BHIE 传完整 5,236,304 B → AMSS 在 MISSION 模式稳定运行（EE=2、MHISTATUS=0x101 干净）→ MHI 通道 ch20/ch21 被设备置成 RUNNING、四条 START_CHAN 命令全部回 COMPLETION。
**唯一卡点**：主机往 ch20 的 TRE 环写入数据描述符并敲门铃后，设备**不消费**（`ch20 rp` 不动、SMMU 上没有任何新 DMA）。已排除 30 余种主机侧原因，判断剩余原因在 AMSS 内部（它还没把 IPCR 数据通道接管起来）。

## 里程碑与决定性证据

| 里程碑 | 结论 | 关键轮次 | 决定性日志 |
|---|---|---|---|
| M4 PBL→SBL | ✅ | p256 | `apply-237 t=311 st 0x80000001 ee 0` → `t=319 st 0x80000001 ee 0x1 mh 0x00000101`（8 ms 内交接） |
| M5 SBL→AMSS | ✅ | p258 | `bhie after 700 ms: status 0xbbd056f0 ee 0x00000002`（10 个向量，全部 5,236,304 B） |
| M6 AMSS 稳定 | ✅ | p279 / p296 / p302 | `apply-252 done ee 0x2 mh 0x101 ctrl 0x0`，15 秒观察无 SYS_ERR |
| M7 通道握手 | ✅ | p304 / p306 | 事件环解出 6 条：STATE_CHANGE(M0)、EE_EVENT(AMSS)、4×CMD_COMPLETION(START_CHAN SUCCESS)；`ch20 0x2 ch21 0x2` |
| M8 数据面 | ⛔ | p305…p332 | `apply-292 send … ch20 wp 0xa020c020` → `apply-297 t=300 ch20 rp 0xa020c000`（不动）、`apply-307 fsr 0x400 gfsr 0`（零 DMA） |

### M4 的真正根因：MSI Message Control 的使能位

EP 的 MSI capability：`conf+0x50` 低 16 位是 **capability ID + next pointer**，Message Control 在 **bit 31:16**，其中 **bit16 才是 MSI enable**。

老代码（apply-220 起一直如此）：

```c
wr(conf.base + 0x50, (cap & 0xffff0000u) | ((cap & 0xfffeu) | 1u));   /* 把 1 OR 进了 cap ID */
```

= 控制字永远是 `0x010a`（enabled=0），**MSI 一次都没真正使能过**。apply-249 改成：

```c
wr(conf.base + 0x50, cap | (1u << 16));   /* 0x010a7005 -> 0x010b7005 */
```

改完第一轮（p256）设备 8 ms 就跳进 SBL。这也解释了此前四个反常现象：状态 311 ms 变 SUCCESS 却没动静、headonly 16 KiB 时状态恒 0、原厂日志里中断与 BHI 完成同刻、p216"加 MSI"没效果。

### M6 的两个前置条件（都不是显而易见的）

1. **不要给主机自己写 MHICTRL 的 M0**。设备在 SBL 阶段已经把自己置成 READY；主机再写 `M0` 会被固件判为越权，4 ms 内置 `0xff05`（SYS_ERR），200 ms 后 AMSS 进 RDDM。原始现象看起来像"AMSS 自己崩了"，实际是主机触发。
2. **ER 门铃必须在 EE=2 之后打，且值必须是环末尾 wp**。在 EE=1 时打门铃，设备直接丢弃；值写环首（`rbase`）而上下文 wp 写环末尾，两者矛盾，设备同样忽略。这一条让前十几次实验里 ER 环"永远是空的"。

### M6→M7 的多米诺：`pcie_chanstart` 复用了 `pcie_mhi_init` 的变量

```c
uint32_t want = pcie_mhi_init;
PE_parse_boot_argn("pcie_mhi_init", &want, sizeof(want));
PE_parse_boot_argn("pcie_chanstart", &want, sizeof(want));   /* 同一个 want */
pcie_chanstart = want;
...
if (want != 0) { /* 整个 MHI 初始化块 */ }
```

传 `pcie_chanstart=0` 会顺手把 `want` 清零 ⇒ **整个 MHI 初始化块一次都不执行**。p290/p291/p293/p294 四轮"EE=2 稳定、无 SYS_ERR"全部是空转（设备自己在跑，主机什么都没做）。apply-285 拆成独立变量后一切归位。**教训：每个 boot-arg 用独立变量解析，且解析前先清零。**

### M2→M0：MHISTATE 不是"不能写"，是"不能在错误的阶段写"

真机 MISSION 模式实测 `MHICTRL = 0x00000400`（**M2**），不是 M0。device 进 MISSION 后自己落 M2；主机要发数据时按 vendor 的 `mhi_pm_resume` 路径先写 M0。

- 从 READY/SBL 直接写 M0 → SYS_ERR（p283/p285/p301）
- 先写 M2（`0x400`，被接受、无错误）→ 再写 M0（`apply-315 m2 to m0: mh 0x00000201`）→ **完全正常，设备继续服务命令环**

这条路径是所有实验里第一次"主机改写 MHISTATE 成功且设备继续工作"。

## M8 精确边界

握手侧全通，数据侧全断：

```
apply-315 m2 to m0:  mh 0x00000201 ee 0x2 ctrl 0x00000200
apply-284 t=0:       er0 rp 0xa0204060（6 事件被消费）ch20 0x1
apply-293 final:     ch20 0x2  ch21 0x2  ch20rp 0x1  ch20wp 0xa020c000
apply-292 send:      tre ptr 0xa020e000 len 0x1000 dw1 0x20200  ch20 wp 0xa020c020
apply-297 t=0/300:   ch20 rp 0xa020c000  wp 0xa020c020      ← 不动
apply-307 fsr:       0x400 (良性位)  gfsr 0                   ← 零 DMA
```

设备在 START_CHAN 之后把 `ch20 rp` 写成 **`0x1`**（不是 IOVA）、把 `wp` 改回环首——它没有把这条通道当 DMA 环在用。

### 已排除清单（别重复）

| 类别 | 试过的 | 结果 |
|---|---|---|
| TRE 格式 | 单条 64 B / 两条 4 KiB，`(2<<16)|(bei<<10)|(ieot<<9)|(ieob<<8)|chain`、ieot=1、ieob=0、chain=0 | 与 vendor `mhi_gen_tre` 逐位一致，无效 |
| 门铃 | 通道门铃 32 位 / 补高 32 位 / 连敲两次 / wake doorbell(0x6F8) 先 1 后 0 / 先 wake 再敲 | 写入都落地（回读一致），设备不理 |
| 通道状态 | chstate=ENABLED(1) / RUNNING(2)、brstmode=0/2/3 | 设备接受写入，但不推进 rp |
| 通道选择 | ch20(IPCR TX)、ch0(LOOPBACK TX)、ch21(RX 预填空 buffer) | 都不消费 |
| 顺序 | SBL 写上下文 / mission 重建 / 发不发 START_CHAN / START_CHAN+rp 复位 | 只有"SBL 写 + mission 发 START_CHAN"能让设备回 COMPLETION |
| 上下文布局 | 0x2c packed / 0x30 带填充 / erindex 0 或 1 | 设备能正确读写这些字段（它确实改过 rp/wp），布局无问题 |
| 地址窗口 | 收窄成 0xa0200000..0xa0a00000 / 真机 0xa0000000..0xb0000000 | 无差异 |
| 环地址 | 指向未映射 0xa0100000（p327） | 设备立刻 SYS_ERR ⇒ **门铃确实传到了它那里，它也会做地址检查** |
| MHISTATE | M0 直接写 / M2 后写 M0 / EE=2 写 M0 / EE=2 写 M2 | 只有"M2→M0"合法 |

### 补充的三轮决定性实验（p333–p335，写本文时刚跑完）

- **p333（`pcie_trap_buf=1`）**：环保持合法，只把 TRE 的 **buffer 指针**指向未映射的 `0xa0100000`。结果 `fsr 0x400 / gfsr 0`、**零 SMMU 故障**、`ch20 rp` 不动。⇒ 设备**根本没有去读那个 buffer**；对照 p327（把**环本身**指向未映射区会立刻 SYS_ERR）说明：门铃→环地址校验这段是硬件做的，**固件并没有真的取走 TRE**。
- **p334（`apply-319`）**：把通道上下文区 `0x300..0x400` 整段 dump 出来，**证实 stride 就是 0x2c**：
  ```
  ctxt[370] 00000002 00000001 00000001 a020c000   ch20: chstate=2 chtype=1 erindex=1 rbase=0xa020c000
  ctxt[380] 00000000 00000200 00000000 a020c000   rbase_hi=0 rlen=0x200 0 rp=0xa020c000
  ctxt[390] 00000000 a020c020 00000000 00000002   rp_hi=0 wp=0xa020c020 wp_hi=0 ch21.chstate=2
  ```
  设备确实把 chstate 改成 RUNNING(2)（我们写的是 1），但 **rp/wp 完全保留我们写的值**，说明它读了上下文却没往下走。
- **p335（`pcie_tre_flags=0x20300 pcie_tre_count=1`）**：单条 TRE、`ieob=1 + ieot=1`、`wp = rbase+0x10` —— 仍然不消费（`ch20 rp 0xa020c000 wp 0xa020c010`）。

- **p336（`apply-321`）**：照真机的时间点复现 —— 命令门铃响后 **5 ms** 就把第一条数据 TRE 塞进 ch20 环（真机是 START_CHAN 完成前 1.5 ms 之后），`tre a020e000 / len 0x34 / dw1 0x20200 / wp 0xa020c010`。结果 `ch20 rp 0xa020c000 wp 0xa020c010` 仍然不动。⇒ 时序也不是原因。

⇒ 到这里可以下结论：**设备侧（AMSS 固件）没有把 ch20 的数据引擎启动起来**。硬件会校验环地址，但取 TRE、推进 rp、发起 DMA 这一整套都发生在固件里，而它没有做。

### 为什么判断是 AMSS 内部

1. 它已经在跑（EE=2、事件环正常、会回命令完成），但**从来没往 ch21 写过任何东西**；
2. 固件里 `mhi_core_process_ring_cb: Issued link request %x from ring %d exceeded max time threshold` 说明它本来会主动发 link request，**我们的 ER 环里从没出现过这类事件**——它连那一步都没走到；
3. 全树 grep：`link request` 只在这一处出现，内核驱动里没有任何代码参与该握手 ⇒ 是固件内部机制。

### 构建

```bash

cd venus-recon && RET=200 bash mk-pcie2.sh pNNN 'pcie=1 pcie_step=5 pcie_power=1 pcie_delay=0 pcie_settle=100 pcie_bar=21 pcie_watch=0 pcie_star_mask=31 pcie_bhi_addr=0xa0004000 pcie_bhi_size=0x80000 pcie_novec=1 pcie_msi_test=1 pcie_mhi_nom0=1 pcie_chanstart=1 pcie_mhi_late0=1 pcie_mhi_state_val=4 pcie_wake2=1 pcie_mhi_data=1 pcie_tag=pNNN'
```

### 跑一轮（必须冷启动）

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
cd venus-recon
& "C:\platform-tools\fastboot.exe" reboot bootloader ; Start-Sleep -Seconds 32
.\run-p104.ps1 -Payload p-pNNN.bin -Tag pNNN -RunSeconds 110
& "C:\platform-tools\fastboot.exe" oem dump logdump 0 40000 ; Start-Sleep -Seconds 3
& "C:\platform-tools\fastboot.exe" get_staged cur-pNNN.bin
```

- `run-p104.ps1` 的 `giving up on seeing the loader go away` / `back in the loader after 30 s` 是**假警报**（xnuloader 的 fastboot gadget 在内核运行时也应答）；
- 它抓的 `ld-pNNN.bin`（1 MB）是**历史分区内容**，常被 `HakiosGPU: submit ...` 刷屏——**只有 `cur-pNNN.bin`（262,144 B，含 `pcie_tag=pNNN`）是本轮日志**；
- 日志环 1 MB，iOS 桌面起来后 GPU 每秒刷 20+ 行，**中段打印会被冲掉**，重要结论必须放在最后一次 printf 附近。

### 设备操作

- 卡死（USB 全灭）→ 长按电源 20 s；
- panic 进安卓 → `adb reboot bootloader`（12–20 s 自恢复）；
- adb 掉线 → `pnputil /restart-device "USB\VID_18D1&PID_4EE7\4F9BAECB"` + `adb kill-server/start-server`；
- **iOS 桌面运行时 USB 完全不枚举，与卡死无法区分 ⇒ 每轮必须问用户屏幕状态**。

## 寄存器速查

### BHI（`bar0 + 0x100`）

`0x00 SOCID / 0x08 IMGADDR_LOW / 0x0c IMGADDR_HIGH / 0x10 IMGSIZE / 0x18 IMGTXDB / 0x20 INTVEC / 0x28 EXECENV / 0x2c STATUS / 0x30 ERRCODE / 0x34-0x3c ERRDBG1-3 / 0x40 SERIALNUM / 0x48 NUMSEG / 0x4c MSMHWID`

- `STATUS` 高两位 = 2 成功、3 失败；低 30 位是门铃序号回显；
- **BHIE 窗口在 `bar0 + 0x224`**：`0x00 MSMSOCID / 0x2c TXVECADDR_LOW / 0x30 HIGH / 0x34 SIZE / 0x3c TXVECDB / 0x44 STATUS`；
- 门铃值：vendor 用随机非零；写 1 也能工作。

### MHI（`bar0 + 0x00`）

`0x00 ID / 0x08 VER / 0x10 CFG / 0x18 CHDBOFF / 0x20 ERDBOFF / 0x28 BHIOFF / 0x30 BHIEOFF / 0x38 CTRL / 0x48 STATUS / 0x58-0x5c CCABAP / 0x60-0x64 ECABAP / 0x68-0x6c CRCBAP / 0x80-0x84 CTRLBASE / 0x88-0x8c CTRLLIMIT / 0x98-0x9c DATABASE / 0xa0-0xa4 DATALIMIT / 0xb0 SOC_RESET_REQ / 0x128 EXECENV`

- 通道门铃 `0x300 + ch*8`，事件门铃 `0x700 + er*8`，命令门铃 `0x70`，wake `0x6F8`（= `CHDBOFF + 8*127`）；
- `CTRL` bits15:8 = MHISTATE（RESET 0 / READY 1 / **M0 2** / M1 3 / **M2 4** / M3 5 / BHI 7 / SYS_ERR 0xFF）；
- `STATUS` bits15:8 = 同上，bit0 = READY，bit2 = SYSERR。

### 真机（Android MISSION 模式）实测值

```
MHICTRL 0x400 (M2)   MHISTATUS 0x401 (M2+READY)   MHICFG 0x00030880
CHDBOFF 0x300  ERDBOFF 0x700  BHIOFF 0x100  BHIEOFF 0xb00
CCABAP 0xa1e29000  ECABAP 0xa1e2a000  CRCBAP 0xa1e2f000
CTRLBASE/DATABASE 0xa0000000   LIMIT 0xb0000000
EXECENV 2   BHI_IMGADDR 0xa1e80000   BHI_IMGSIZE 0x80000
```

### MHI 上下文（`struct` 全 `__packed`，stride 0x2c）

| 字段 | 通道 | 事件 | 命令 |
|---|---|---|---|
| word0 | chstate:8/brstmode:2/pollcfg:6/rsvd:16 | rsvd:8/intmodc:8/intmodt:16 | — |
| 0x04 | chtype | ertype | — |
| 0x08 | erindex | msivec | — |
| 0x0c | rbase | rbase | rbase |
| 0x14 | rlen | rlen | rlen |
| 0x1c | rp | rp | rp |
| 0x24 | wp | wp | wp |

### 事件 TRE

`struct mhi_tre { u64 ptr; u32 dword[2]; }`，16 字节：

- `dword[1] >> 16` = 类型：`0x20` STATE_CHANGE、`0x21` CMD_COMPLETION、`0x22` TX_EVENT、`0x40` EE_EVENT、`0x48` TSYNC；
- CMD_COMPLETION：`ptr` 指向主机写的原 TRE，`dword[0]` 低字节 = 状态（1 = SUCCESS）。
- 数据 TRE：`dword[1] = (2<<16)|(bei<<10)|(ieot<<9)|(ieob<<8)|chain`。

## 反汇编调查（2026-11-10 凌晨，结论是"此路不通"）

目标：在 `amss.bin` 里定位 MHI 通道启动逻辑，看设备为什么不消费数据 TRE。

### 已确认的事实

1. **固件是 Thumb-2，不是 A32。** 按 A32 编码扫描，全镜像 `movw/movt` 命中 0 条、`ldr/str [rX, #0x38/0x48/0x58/0xb0]` 命中 0 条——这不合理；按 Thumb-2 扫描同一镜像立刻命中 434 条 `movw/movt`。**之前所有基于 A32 的“无引用”结论全部作废。**

2. **seg9 里没有代码。** seg9 = file `0x165000` / VA `0x15f8000` / size `0x192c0`，里面是 CE 与 MHI 的日志格式串。用 `arm-none-eabi-objdump -D -b binary -m armv7 -M force-thumb --adjust-vma=0x15f8000` 反汇编出 48,636 行，**`movw` 命中 0 条**——全是被误当作指令解码的 ASCII。

3. **MHI 字符串没有任何 32 位指针指向。** 全镜像搜 `0x0160a168`、以及 `0x0160a000–0x0160a400` 整个区间：**0 个命中**。改用 Thumb movw/movt 配对构造该地址：**0 个命中**。换成 `0x160a174`、`0x160a195`、`0x160a22a`、`0x160bc58`、`0x160d0ed` 同样 0 个。

4. **但同一段里更早的字符串是有指针的。** `0x17715c` 处有两个 32 位字 `0x01609ed3`、`0x01609f01`，指向 CE 相关的格式串。⇒ 这份镜像的“指针指向字符串”机制是存在的，只是**恰好没有指针指向 MHI 那一组**。

### 由此得到的判断

MHI 那组格式串（`mhi_patch.c`、`mhi_core_process_ring_cb`、`link request`、`linkReqQ`、`IPCR`）在本镜像里**是未被引用的死数据**，对应日志路径很可能在编译时被裁掉或走了另一套机制。**以字符串为锚点反汇编这条路到此为止**，继续挖只会空转。

### 如果还要继续 RE，可用的替代锚点（按性价比排序）

1. **通道上下文 stride `0x2c`**：找 Thumb-2 里 `movs rX, #0x2c` + `mla`/`mul` 的组合，那几处就是上下文索引代码。
2. **MHI 寄存器基址**：固件访问 MHI 时用的是一个基址寄存器 + 偏移，先找 `ldr rX, [rY, #0x38]`（`F8D?0038` 编码）在哪个函数里成组出现（`0x10/0x18/0x20/0x38/0x58/0x60/0x68` 一串），那一组就是 MHI 初始化。
3. **对照另一份 QCA6490 固件**（OnePlus 9 的 `amss.bin`，5,178,848 B，star 板表 crc `0x7b19c475`）做二进制 diff，差异区就是机型相关的，相同区就是 MHI 核心。

### 在此之前，M8 的硬件侧结论不变

设备在 SBL 阶段会回 4 条 `START_CHAN` 的 `CMD_COMPLETION`、会把 `chstate` 改成 `RUNNING`、会消费 `STATE_CHANGE(M0)` 与 `EE_EVENT(AMSS)`；但**从不推进任何数据通道的 `rp`**，即使 TRE 合法、`ieot/ieob` 正确、buffer 指向合法内存、门铃在 START_CHAN 完成后 5 ms 内就敲（p336）。把环指向未映射区会立刻 `SYS_ERR`（p327），说明硬件做了环地址校验——**取 TRE 这步发生在固件里，而固件没做**。

### 追加（同一晚稍后）：镜像主体不是可直接反汇编的机器码

| 检查 | 结果 |
|---|---|
| Thumb-2 `ldr.w Rt,[Rn,#imm12]`（`F8Dx`）全镜像 | 191 条 |
| A32 `ldr rX,[rY,#imm12]`（`E59x`）全镜像 | 0 条 |
| seg2（入口 `0x1439500` 所在段，117 KB）按 Thumb 反汇编 | 全是 `bne.n / ldr r0,[r0,r0]` 这类无意义序列 |
| 同段按 AArch64 反汇编 | 大量 `<unknown>` |
| seg2 熵 | 6.656（`seg12` 6.854，`seg8` 3.537，`seg9` 5.807，`seg14` ≈ 0） |

⇒ **`amss.bin` 的 PT_LOAD 内容既不是 A32、也不是 Thumb-2、也不是 AArch64 的明文代码**，熵 6.6–6.9 与压缩流一致。只有 seg9 那一段是可读字符串。

结论：**静态反汇编这条路在拿到解压/解码方式之前走不通**。PBL 会校验 ELF 头（p217 证明），但段的载荷它大概是原样搬到芯片 RAM、由芯片自己的引导逻辑解释——这也解释了为什么我们改段内容 PBL 毫无反应（p223/p224：它本来就不读）。

### 因此，M8 之后若要继续，现实的三条路

1. **拿另一份同芯片固件做二进制比对**（OnePlus 9 / `star` 的 `amss.bin`，5,178,848 B，crc32 `0x7b19c475`）——若两份在同偏移处结构一致，说明是同一套编码；若某段只在一份里出现，那就是机型差异。
2. **放弃静态逆向，改做行为观测**：真机上 WiFi 能连路由，说明同一颗芯片能走完 MHI 数据面。差别只在主机侧。可以尝试把我们的通道上下文布局、IOVA 布局**逐字节对齐真机**（真机：`CCABAP 0xa1e29000 / ECABAP 0xa1e2a000 / CRCBAP 0xa1e2f000`，BHI staging `0xa1e80000`，均在 IOVA 池高位；我们用 `0xa020xxxx`）。
3. **接受当前边界**：M4/M5/M6/M7 全通，M8 卡在厂商固件内部，把结论整理成文档，等有别的切入点再回来。

### p337（apply-322：把 RX 环按真机方式填满 32 个 0x8000 buffer）—— 仍然无效

真机 `mhi_uci` open 时 `mhi_queue_inbound()` 会把 ch21 的整条环（32 项）填满空 buffer，我们此前只填过 2 项，怀疑设备在等整环。p337 直接照真机做法填满 32 项：

```
apply-322 rx primed 32: rx[0] a0500000 00000000 00008000 00020200 rx[1f0] a05f8000 00000000 ch21 wp 0xa020d200
apply-322 after the rx bell: ch21 rp 0xa020d000 wp 0xa020d200 buf0 00000000 er0 rp 0xa0204060
apply-293 final rp 0xa0204060 wp 0xa0204ff0 ch20 0x00000002 ch21 0x00000201 mh 0x00000201 ee 0x00000002
apply-292 send: tre ptr 0xa020e000 len 0x1000 dw1 0x00020200 ch20 wp 0xa020c020
apply-297 t=0/300 ms ch20 rp 0xa020c000 wp 0xa020c020 ... chdb 0xa020c020 mh 0x201 ee 0x2
```

两个新观察：

1. **RX 环也没被消费**（`ch21 rp` 停在 `0xa020d000`，设备没往任何 buffer 写东西）。
2. **ch20 变 RUNNING(0x2)，而 ch21 停在 `0x201`(ENABLED)** —— 设备只改写了 TX 通道的上下文，RX 通道没动。这让"设备根本没启动 ch21"这个可能性变得很具体。

结论不变：主机侧已经把 vendor 在 `mhi_uci` 路径上做的事全做了一遍（写上下文 → START_CHAN → 填 RX 环 → 敲门铃 → 塞 TX TRE → 唤醒门铃），设备只在命令环上回应，数据面一步都不走。

## 十一、p349–p352：RDDM（固件崩溃转储）尝试与结论（2026-11-10 02:30–02:50）

### 目的
M8 卡在“设备不消费 TX TRE”。主机侧已与 vendor 源码逐条对齐（Gen2、BW_SCALE 广告与应答、M0/EE、事件环、命令环、通道上下文全通），
黑盒排除已到尽头，于是想直接拿固件的崩溃转储，让固件自己说明为什么不启动数据引擎。

### 做了什么
1. **apply-332**：照 vendor `mhi_rddm_prepare()` 建 RDDM 向量表（9 段 × 512 KiB），
   写 BHIE 接收寄存器 `0x224+0x60/0x64/0x68/0x70`（地址、长度、序号），然后故意让设备出错，400 ms 后读回。
2. **p349（首轮）**：`apply-332 rddm table 0xa0820000 rxvec ... st 5c017e67`，`seg0 nz 16384 of 16384`，
   还扫出固件字符串 `FemHighIsolationMode` —— 看着像成功。
3. **p350（加字符串扫描）**：只命中 1 条，`apply-333 hits 1`。
4. **发现假象**：RDDM 缓冲区放在 `0xa0400000`，而 `amss.bin` 整镜像副本位于 `0xa0220000` 起 5 MB（结束于 `0xa071fa50`）——
   `0xa0400000` 正好落在镜像里。读到的全是自己拷进去的固件，不是转储。
5. **p351（挪到镜像之外）**：表 `0xa0990000`，5 段从 `0xa0720000` 起。结果 `apply-332 seg0 nz 0 of 16384, apply-333 hits 0` —— **一个字节都没写**。
6. **p352（按 vendor 顺序重做）**：先清零 BHIE 接收寄存器（vendor 注释：上电值未定义），再写向量表，
   然后用 vendor `mhi_force_rddm_mode()` 的方式往 `MHICTRL` 写 `0xFF00`（SYS_ERR 状态）强制进 RDDM。

### 结果
```
apply-332 rddm table 0xa0990000 rxvec 00000000 a0990000 00000060 db 00003320 st 00000000
apply-334 t=0    ms mh 00000101 ee 00000001 rxst 00000000
apply-334 t=600  ms mh 00000101 ee 00000001 rxst 00000000
apply-334 t=1200 ms mh 00000101 ee 00000001 rxst 00000000
apply-334 t=2400 ms mh 00000101 ee 00000001 rxst 00000000
apply-332 after the error: mh 00000101 ee 00000001 rxst 00000000
```
**设备不理会主机写的 SYS_ERR**：2.4 秒内 MHISTATUS 恒 `0x101`、EE 恒 1（SBL）、RX 状态恒 0、缓冲区空。

### 结论
- 主机无法把设备“推”进 RDDM；vendor 能收转储是因为**设备自己崩进 RDDM（EE=3）**之后它才去读。
- 我们的固件在 SBL 阶段根本走不到那一步，所以这条内省渠道在 M8 阶段不可用。
- 三次运行 RX 状态寄存器低位（序号）都不是我们写的 `0x3320`、高位恒为 1 ⇒ 向量表从未被设备确认。

### 教训（写进“别再做的事”）
- **RDDM 缓冲区不能放在镜像区**：`0xa0220000 + 0x4fe650` 一直是有效镜像，落在其中的任何“转储”都是自己的固件副本。
- **写 MHICTRL 的 SYS_ERR 状态不会强制 RDDM**，只会让设备按非法主机行为处理（MHISTATUS 置 0xff05）。
- 读到的数据先核对“是不是我们自己写进去的”，这次差点把固件副本当成转储。

## 十三、06:00–07:00 的九轮（p388–p396）：根因、事件环真相、mission 被拒

### 13.1 找到了“重编内核 M0 被拒”的真根因（apply-350/351，p388/p389）
`hakios.pcie.c:2304-2315` 的 boot-arg 解析被我自己后续的补丁套成了三层：
`if (parse pcie_mhi_nom0) { want2 = 0; if (parse pcie_rp_fix) { want2 = 0; if (parse pcie_m0_delay) {…} pcie_rp_fix = want2; } pcie_mhi_nom0 = want2; }`
`want2` 被反复清零 ⇒ **`pcie_mhi_nom0` 恒为 0**，无论 cmdline 写什么，SBL 阶段都会写 `MHICTRL=0x200`，
设备当场 `MHISTATUS=0xff05`（p385 去掉 `pcie_mhi_late0` 仍 0xff05，因为 M0 是从这个坏门控里进去的，与 late0 无关）。
apply-351 拆成三个独立解析块后，重编内核行为与老内核完全一致：`apply-270 m0 skipped … ctrl 0x0` → `apply-286 m0 after mission: mh 0x201` → `ctxt[370] … RUNNING`。
**教训：所有 boot-arg 解析块必须各自独立，不得共用变量；每加一个补丁就 `strings | grep apply-` 核对。**
（顺带作废两条：`pcie_retrain=1` 不是变量——p383/p384 的 `apply-330 retrained … 0x80 = 0x10110008` 完全一样；物理地址也不是变量。）

### 13.2 p391：数据面整体搬到 0xa1c00000 —— 正常
`#define PCIE_EXTRA_IOVA 0xa1c00000ull`（apply-354，一处改，镜像/上下文/环/缓冲全搬）。
`smmu: image region 0xa1c00000 -> 0x192d2c000, 2048 pages`、`ccbap 0xa1c00000 ecbap 0xa1c02000 crcbap 0xa1c02400`、ch20 `RUNNING`、门铃回读 `chdb 0xa1c0c020` 连续 8 条一致。
**设备仍不取 TRE**。搬家不是解法，但证明 SMMU 映射与门铃落盘都正确。

### 13.3 p392/p393/p394：mission（state 4）被固件拒收
真机 WiFi 正常时 `MHICTRL/MHISTATUS = 0x400/0x401`（state 4），我们一直是 `0x201`（state 2）。三种走法全部失败：

| 轮次 | 动作 | 结果 |
|---|---|---|
| p392 | 通道 RUNNING 后直接写 `4<<8` | `ctrl 0x400` 读回成功，`mh` 仍是 0x201 |
| p393 | `2 → 1 → 4` 逐级走 | 两次都 `mh 0x201` |
| p394 | `pcie_mhi_state_val=1` 停在 0x101，再写 4 | `mh 0x101` 不动 |

⇒ **这颗固件只接受过一次 state 请求（EE=1 → 0x201），之后写 1 或写 4 都被无声丢弃**：`MHICTRL` 读回我们写的值，`MHISTATUS` 纹丝不动。
“主机单方面写 MHICTRL 就能进 mission”这条路走死。

### 13.4 p395：ER0 整环原始转储 —— 设备一共只发过 2 个事件
```
apply-357 er0 ctx rp 0xa1c04020 wp 0xa1c04ff0
er[00] 0140e4f4 00899183 02000000 00200000  type 20 (STATE_CHANGE)
er[01] 0140e4f4 00899183 02000000 00400000  type 40 (EE_EVENT)
er[02..1f] 全 0
```
两个事件都把 EE=2 写在 `w2` 高字节；**没有任何 CMD_COMPLETION（type 0x21）**，且设备的 `wp` 从不更新。
同一轮 `ctxt[370] … 00000002`（ch20 RUNNING）、`ctxt[3a0] … 00000201`（ch21 仍 ENABLED）——**通道状态被改与事件投递是解耦的**。

### 13.5 p396：修 ER 上下文 wp 初始化（apply-358）—— 无变化
`apply-269` 把事件环 `wp` 初始化成 `rbase+0xff0`（“最后一个元素”，那是 TX 环的约定）。apply-358 改成 `rp == wp == rbase`：
`apply-357 er0 ctx rp 0xa1c04020 wp 0xa1c04000`，**仍然只有那两个事件**。⇒ 该假设也排除，设备在 EE=2 之后就不再往 ER0 写任何东西。

### 13.6 当前判断与下一步
- 设备侧：EE=2 之后事件流只剩开机那两条；命令环能看到 chstate 变 RUNNING；数据环完全静默。
- 与 p348 基线（那时 er0[2] 里还有一条 `0x21` 完成事件）相比，现在的构建少了这条完成事件，
  最大变量是 **apply-354 的搬家**（0xa0200000 → 0xa1c00000）与 apply-351~358 的补丁堆叠。
- 建议的 A/B：把 `PCIE_EXTRA_IOVA` 改回 `0xa0200000`（保留 `pcie_erfull`），冷启动跑一轮，直接对比 ER 流是否恢复三条事件。
  若恢复 ⇒ 搬家暴露了固件对 IOVA 区间的隐含假设（真机把 MHI 缓冲放在 0xa1d…–0xa1f…）；若不恢复 ⇒ 是补丁堆叠改变了时序。
- 之后才谈 QMI 首包（第十二节的结论仍然成立：这是协议实现，不是寄存器实验）。

### 13.7 p397：A/B 结论 —— 搬家不是原因
`apply-359` 把 `PCIE_EXTRA_IOVA` 改回 `0xa0200000`（保留 `pcie_erfull`），冷启动：
```
apply-357 er0 ctx rp 0xa0204020 wp 0xa0204000 mh 0x00000201 ee 0x00000002
er[00] 0140e4f4 00899183 02000000 00200000  type 20
er[01] 0140e4f4 00899183 02000000 00400000  type 40
er[02..] 全 0
```
⇒ **两个地址上的事件流完全一样，都只有 2 条**。搬家与 ER 事件数无关；p348 当时 `er0[2]` 里那条 `0x21` 很可能就是上一轮残留的旧数据（同一块物理内存在多次启动间复用），
也就是说“设备发过 CMD_COMPLETION”从来没有被真正证实过。**下一步应当先证伪这一点**：把 chstart 上下文里的 chstate 故意写成 1，
看设备是否会自己把它改成 2 —— 如果不会，那此前所有“设备处理了 START_CHAN”的结论都要重新审视。

### 13.8 p398（apply-360）决定性结果：**设备在 EE=2 之后是死的**
把 ch20 上下文的 `chstate` 手动改回 1，等 200 ms 再读：
```
apply-360 ch20 state forced to 1: was 0x00000002 now 0x00000001
apply-360 ch20 state after 200 ms: 0x00000001 (1 = device inert)
```
⇒ 设备**没有**把它改回 2。也就是说此前看到的 `chstate = 2 (RUNNING)` 是我们自己 apply-282/apply-308 写进去的，
`rp = 0x1:0x1` 那条“设备覆盖”的记录同样是宿主写的结果。**设备从未碰过任何通道上下文。**

结合 13.4/13.5/13.7：唯一的设备侧输出只有开机时那两条事件（STATE_CHANGE state=0 + EE_EVENT，均带 EE=2），
之后设备对命令门铃、通道门铃、ER 上下文、MHICTRL 状态请求全部无反应。

**M8 的表述必须改写**：不是“设备不取 TRE”，而是“AMSS 起来之后它根本没有把 MHI 客户端拉起来”。
下一步方向：查固件在 EE=2 之后期望什么（BHI 唤醒 / MHI 配置寄存器的时序 / 镜像段表），而不是继续调 TRE 格式。

### 14.3 事件环真相（p395/p396/p397/p405）

- 擦净实验（apply-365 把 `0x4000..0x5000` 清零后）设备仍写回 2 条 TRE ⇒ **事件环设备→主机通路是通的**，那 2 条是设备真写的（STATE_CHANGE `0x20` + EE_EVENT `0x40`）。
- 设备**从不更新事件上下文里的 wp(0x24)**（擦净后 rp/wp 都还是基址）⇒ 主机只能扫 TRE 判断有无新事件。
- wp 初值（`rb+0xff0` vs `rb`，p396）与搬家（p397 A/B）都与事件数无关；p348 那轮 `er0[2]` 的 `0x21` 很可能是同一块物理内存上一轮残留。

### 14.4 通道上下文的正确语义（vendor `mhi_internal.h:261`）

```
struct mhi_chan_ctxt {
	u32 chstate:8; u32 brstmode:2; u32 pollcfg:6; u32 reserved:16;  /* 0x00 */
	u32 chtype;   /* 0x04 = mhi_chan->type            */
	u32 erindex;  /* 0x08 = mhi_chan->er_index（不是 ee！）*/
	u64 rbase 0x0c | u64 rlen 0x14 | u64 rp 0x1c | u64 wp 0x24
};  /* stride 0x2c */
```
- `ch20[00]=0x00000002` 是设备写的 **chstate=RUNNING**；
- 我们此前写的 “ee=2” 实际改的是 **erindex**；
- `mhi_cmd_ctxt` 的三个 u32 全是 reserved，命令环 `0x04` 写 0 或 1 **都不影响**（p414 对照实验：写 0 也照样收到 4 条 COMPLETION）⇒ 之前“`type=1` 修好命令环”是**假阳性**，已把默认值改回 0；
- 数据 TRE `0x00020200 = (2<<16)|(1<<9)` 与 `MHI_TRE_DATA_DWORD1(bei,1,0,0)` 一致，格式正确。

### 14.6 其它已关闭的点

- **IMGSIZE**：p416 显示写入前它已经是 `0x80000`（与真机 `BHI_IMGADDR 0xa1e80000 / IMGSIZE 0x80000` 一致），5 MB 只是我们自己摆进 DDR 的镜像，两者无关。
- **`mhi,m2-no-db-access`**（`mhi_init.c:1511-1513`）：venus 的 `db_access` 只有 M0，`MHI_DB_ACCESS_VALID` 在 M2 为假，vendor 驱动在 M2 下**不会** `mhi_ring_chan_db`。我们一直在 M0(`0x201`) 下敲门铃，这一条尚未构成矛盾，但值得在下一轮作为“设备也许在等 wake 而不是门铃”的线索。
- **门铃写序**：apply-300 起已是 vendor 语义（先 `+4` 再低半），无需改。

### 14.8 p417–p420：两条新路径的排查结果（2026-11-10 上午）

1. **vendor 加载序列 = 我们（drivers/bus/mhi/core/mhi_boot.c）**
   :388 mhi_fw_load_bhi()（写 IMGADDR/IMGSIZE → 敲 BHI 门铃 → 等 BHI_STATUS + EE=SBL）
   :643 ret = mhi_fw_load_bhi(...)
   :333 mhi_fw_load_bhie()（写 BHIE 向量表 → 逐段传 → 等 EE=AMSS）
   :711 ret = mhi_fw_load_bhie(...)
   ⇒ BHI 之后没有任何额外寄存器动作，我们这一层与 vendor 等价，**问题不在加载器**。

2. **真机 dmesg 没有 MHI 日志**：dmesg | grep -i mhi 零输出（vendor 关了 MHI_VERB），
   “BHI transfer complete”之类的对照时间戳拿不到 ⇒ 第 1/2 条对照路径作废。

3. **真机固件走 sysfs fallback**：
   cnss_pci 0000:01:00.0: Direct firmware load for qca6490/amss.bin failed with error -2 →
   Falling back to sysfs fallback for: amss.bin，由 cnss-daemon 推镜像；真正发起 BHI 的仍是 mhi_boot.c。
   pci.c:1370 的 "Notify MHI to use already allocated images" 是崩溃转储用的 bc_image/rddm_image，与加载无关。

4. **真机 WLFW 服务启动后会断一次再重连**：
   [32.777924] wlfw_start: Starting → [38.133666] wlfw_qmi_err_cb: Server disconnect, err -2 → [38.134036] wlfw_start: Starting
   ⇒ AMSS 起来后确实存在一段“服务未就绪”期，可作为后续判读 AMSS 是否真的跑起来的外部旁证。
